De-Para: o que mudou

Comparação lado a lado entre o estado inicial do repositório e o estado final após a execução.

ANTES Telegram acoplado ao núcleo
  • Envelope IPC com from/chat numéricos: IDs de canal do Telegram vazam para o núcleo e o state.json
  • Boot por provedor específico: só telegram, sem registry de provedores
  • Erros de provedor por instanceof, sem código canônico para classificar
  • Sem agentes: nenhum comando, dispatcher ou relatório de run
  • Painel sem estado dos agentes e sem botão de cancelamento
DEPOIS Mensageria neutra + agentic no host
  • Envelope IPC V2 neutro: from/chat string, provedor declarado nas respostas
  • Boot genérico por provedor: telegram + discord como adapters no registry
  • ProviderError canônico por código numérico — errors.ts com cobertura 100%
  • Dispatcher de agentes no host: allowlist default-deny, nonce 2 etapas, agent.report ≤64 runs
  • Painel com bloco 🤖 Agentes: lista de runs ativos + cancelamento

Impacto

O que cada mudança significa para quem usa o deep-orchestrator:

Desacoplamento de provedores

Novo provedor = novo adapter no registry. O núcleo, o worker e o painel não conhecem mais o Telegram por nome.

Discord nativo sem SDK

REST fetch + Gateway WebSocket nativos do Node 24: 0 dependências novas para um provedor completo.

Agentic no host

Dispatcher real com ctx.subagents, allowlist default-deny de skills e teto maxRuns 1..32 — fail-closed.

Qualidade

2642 testes no gate final, cobertura errors.ts 100%, revisão adversarial por onda com todos os HIGHs corrigidos (4 fixes).

Novas capacidades

  • ✓ /agente <skill> <prompt> — dispara um run de agente com confirmação em 2 etapas (nonce)
  • ✓ /agentes — status dos runs ativos com relatório do agente
  • ✓ /parar-agente <id> — cancela um run ativo pelo identificador
  • ✓ Painel com bloco 🤖 Agentes — lista de runs + botão de cancelamento (CSRF protegido)
  • ✓ Difusão proativa do agent.report quando um run termina, no canal que o pediu
  • ✓ Suporte Discord configurável — INSTALL + ONBOARDING-DISCORD com token e apiRootVar
  • ✓ Skills de bot atualizadas (dsh-provider-bot e dsh-telegram-provider) para o envelope V2

Premissas inferidas sem perguntar

O orquestrador opera em autonomia total — nenhuma pergunta é feita ao usuário. Toda premissa assumida fica registrada aqui — para revisão e reprodutibilidade.

Envelope IPC V2 neutro: from/chat viram string e o provedor passa a ser declarado — o núcleo deixa de conhecer o Telegram.
Worker agnóstico de provedor: boot genérico e ProviderError por código numérico (nunca por instanceof), com sonda por provedor.
Security fail-closed em agents: allowlist default-deny de skills, teto maxRuns 1..32 e nonce server-side no host.
Discord sem SDK: só REST fetch + WebSocket nativos — zero dependências novas no projeto.
Sonda de boot por provedor: criada no boot genérico com apiRootVar por provedor (DISCORD_API_ROOT etc.).
Revisão adversarial por onda: revisor em cada onda, todos os HIGHs corrigidos (4 fixes) antes da integração.
