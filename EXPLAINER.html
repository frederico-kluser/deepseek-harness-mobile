De-Para: o que mudou

Comparação lado a lado entre o estado inicial do repositório e o estado final após a execução.

Antes

O bot do Telegram se configurava 100% por CLI, e o acesso era invisível.

  • Token colado via dsh-guard-setup no terminal (sem nenhuma rota HTTP)
  • Estado do bot era só um botão OFFLINE/ONLINE no chrome antigo via tapIndex
  • Nenhuma forma de ver quem estava acessando o túnel (sockets opacos, sem IP/device/contagem)
  • Plugin externo NUNCA tinha contribuído UI para os slots do DSH (mecanismo não provado)
Depois

Painel completo dentro do modal de settings do DSH, 100% via interface.

  • Aba "Telegram Guard" (slot settings.section): badge Configurado/Não configurado/Env + Bot ONLINE/OFFLINE
  • Form de token (password + toggle) → valida getMe → grava 0600 → reinicia o worker; 409 honesto se o env manda
  • Instruções copiáveis (/parear, /ligar, /status, /rotacionar, /desligar, /emergencia)
  • Métricas de acesso: conexões ativas + sessões vivas + lista (device, tempo, IP quando confiável), refresh 15s
  • Botão "Telegram" ao lado do settings (sidebar.footer.action) abre o modal já na aba nova

Impacto

O que cada mudança significa para quem usa o deep-orchestrator-agent-skill:

Configuração do Telegram sem terminal — o dono cola o token e valida direto na GUI do DSH; a CLI continua existindo mas deixa de ser a única via
Visibilidade de quem acessa — conexões ativas, sessões vivas, device (user-agent normalizado), tempo de uso e IP (quando a borda é confiável); decisão informada para rotacionar/derrubar
Prova do mecanismo de UI de plugin — primeiro plugin externo a contribuir slots no DSH (dsh.client + exports ./package.json + closure-factory), repetível por qualquer provedor futuro
Honestidade do estado — o painel nunca afirma "configurado" quando o env TELEGRAM_BOT_TOKEN manda (409 com instrução) e nunca mostra handle de token não gravado
Privacidade por construção — sessões expostas como hash truncado, UA normalizado, IP só de cf-connecting-ip confiável; token/?key nunca no bundle, na projeção ou no log

Premissas inferidas sem perguntar

O orquestrador opera em autonomia total — nenhuma pergunta é feita ao usuário. Toda premissa assumida fica registrada aqui — para revisão e reprodutibilidade.

  • UI
    Slots nativos do DSH, zero patch no harness — client-half via dsh.client (exports ./client + ./package.json) + ctx.slots.register; a pedra de toque era o exports ./package.json (sem ele o registry rejeita silenciosamente)
  • modal
    Abrir o modal do settings já na aba nova — o open é estado local do SettingsRoot sem handle global; affluent DOM (clique no trigger escopado ao .settingsArea + clique no rail de 'Telegram Guard'), provado em headless
  • token
    Token 100% via interface com honestidade — POST valida formato→getMe→grava 0600 atômico→restart; 409 token-por-env quando o ambiente manda (nunca mentir que configurou)
  • privacidade
    Métricas sem vazar segredos — sessões expostas como hash truncado (8 chars), UA normalizado, IP só quando cf-connecting-ip confiável; ?key/token nunca no bundle nem na projeção
  • CSRF
    Fonte própria de CSRF — GET /api/csrf (HMAC stateless, mesmo binding) para o bundle não depender do meta do chrome antigo
  • dist
    Instalação por git funcional — prepare roda build:all (gera lib/client.js + dist); check-tarball exige lib/client.js
